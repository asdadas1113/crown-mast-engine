# 1연구 실행 재현성 및 기록 규격

## 1. 목적

이 문서는 1연구를 실제로 실행할 때 어떤 정보를 반드시 저장해야 하는지 정의한다.

1연구의 목적은 대표적인 Crown/Mast 조건에서 넓은 roster·성장·환경 조합을 탐색하고 전체 경향과 후속 연구가 필요한 특이 사례를 찾는 것이다. 결과 수치뿐 아니라 같은 입력과 코드로 재실행할 수 있는 provenance를 함께 보존한다.

## 2. 재현성 원칙

각 공식 실행은 최소 다음 네 층을 구분해 기록한다.

1. 연구 정의
2. 코드 상태
3. 캐릭터 데이터 상태
4. 개별 scenario 입력과 결과

이 중 하나라도 누락되면 정식 1연구 결과로 취급하지 않는다.

## 3. 식별자

### study_id

현재 1연구의 고정 식별자:

```text
crown-mast-study-01-exploratory-v1
```

같은 연구 정의 안에서는 변경하지 않는다.

### run_id

같은 study_id 아래에서 실제로 수행한 한 번의 실행 묶음을 식별한다.

코드·데이터·실행 조건이 달라진 재실행은 기존 run을 덮어쓰지 않고 새 `run_id`를 사용한다.

### case_id

동일 연구 정의 안에서 편성·성장점·환경점으로 결정되는 개별 scenario 조건을 식별한다. 코드와 데이터 동일성은 `case_id`만으로 보장하지 않으므로 run manifest의 Git SHA와 catalog revision/hash를 함께 기록한다.

## 4. run별 저장 위치

공식 실행은 다음 구조로 저장한다.

```text
research_results/studies/01_exploratory/
├─ machine/
│  ├─ manifest/manifest_template.json
│  └─ runs/<run_id>/
│     ├─ manifest.json
│     ├─ scenarios/
│     ├─ raw/
│     ├─ aggregate/
│     └─ provenance/
├─ human/
│  └─ reports/<run_id>/
└─ validation/
   └─ runs/<run_id>/
```

템플릿은 덮어쓰지 않는다. 실제 manifest는 반드시 `machine/runs/<run_id>/manifest.json`에 새로 만든다.

## 5. 실행 단위 manifest 필수 항목

각 run에는 하나의 최상위 manifest를 둔다.

필수 항목:

- `schema_version`
- `study_id`
- `run_id`
- `status`
- `generated_at`
- 실행 branch와 정확한 Git commit SHA
- `engine_rule_revision`
- `skill_hook_revision`
- `skill_hook_factories`
- `catalog_source_revision`
- `catalog_sha256`
- `study_definition`
- `timeline_definition`
- 결과/scenario schema version
- 실행 전후 validation 참조
- 각 output shard의 파일명·크기·checksum

## 6. 캐릭터 데이터 변경 실험

표준 catalog와 다른 스킬 수치 override를 사용한 실험은 정식 기본 표본에 섞지 않는다. override가 필요하면 별도 run 또는 validation으로 분리하고 catalog revision에 변경 actor·skill·field·value가 식별되도록 기록한다.

## 7. 개별 scenario 보존 항목

각 scenario record에는 최소 다음 입력을 보존한다.

- `case_id`
- roster 전체와 Main/Secondary 역할
- 각 캐릭터의 실제 최종 build
- gear / collection(SR) / overload ATK·Element·Ammo 값
- boss DEF / boss element / core hit rate / range bonus
- Main advantage 실제 적용 조건
- combat duration / startup delay / min firing rounds adjustment
- baseline rotation
- RAID14 burst timeline
- 예상 engine/catalog/hook revision

애장품 캐릭터는 SR15 canonical floor를 적용하므로 profile 이름만 저장하지 않고 실제 해석된 build를 함께 저장한다.

## 8. scenario/raw 저장 형식

28,188 scenario를 각각 하나의 Git 파일로 만들지 않는다. 수만 개의 작은 Git object는 저장소 크기와 checkout 비용을 불필요하게 키운다.

따라서 다음 원칙을 사용한다.

- `scenarios/`: shard 단위 JSONL 또는 CSV
- `raw/`: shard 단위 JSONL, 필요하면 gzip 압축
- shard는 case ID 범위 또는 roster 묶음 기준으로 결정
- 각 shard에 record 수와 checksum을 manifest/provenance에 기록
- 중간 실패 shard는 completed shard와 구분
- aggregate는 raw와 별도로 CSV/JSON 형태로 생성

최종 shard 크기는 공식 실행 스크립트의 writer smoke test에서 정하되, case 순서와 case ID는 항상 재현 가능해야 한다.

## 9. 기계용 결과 구분

- `manifest.json`: 실행 전체 정의
- `scenarios/`: 실제 실행 입력
- `raw/`: scenario별 원시 계산 결과를 담은 shard
- `aggregate/`: 집계 결과·요약 통계
- `provenance/`: 실행 환경·revision·checksum·CI 참조

사람용 해석은 `human/reports/<run_id>/`에 별도로 작성한다.

## 10. 정식 결과 인정 조건

아래 조건을 모두 만족해야 정식 1연구 결과로 취급한다.

1. 사용자 명시적 실행 승인이 있었다.
2. 실행 전에 `study_id`, `run_id`, 실행 Git SHA가 고정되었다.
3. manifest가 실행 전에 생성되었다.
4. catalog source revision/content hash가 기록되었다.
5. engine rule/skill hook signature가 기록되었다.
6. 모든 scenario 입력이 보존되었다.
7. 실행 전 validation gate가 통과했다.
8. raw와 aggregate가 분리되어 저장되었다.
9. shard별 record 수와 checksum이 검증되었다.
10. 실패·중단·부분 실행을 completed run과 섞지 않았다.
11. 실행 후 validation 기록이 같은 `run_id`에 연결되었다.

## 11. 현재 상태

2026-09-07 기준:

```text
study_id = crown-mast-study-01-exploratory-v1
87 rosters × 27 growth × 12 environments = 28,188 scenarios
execution model gates = 0
execution_ready = true
status = design-frozen-execution-unapproved
```

검증된 engine commit `801cab5fa3b0d64150ea0ebd9558acce6bce47ba`에서 focused 19/19, full regression 327/327, no-simulation case-generation 28,188/28,188이 통과했다. GitHub Actions `34002759044`의 322-test 결과는 이전 2026-09-06 검증 기록으로 유지한다.

공식 전투 batch는 아직 실행하지 않았으며 실제 `run_id`, run manifest, raw/aggregate 결과도 없다.

1차 연구 후 코드가 변경되면 완료된 run은 불변으로 보존하고 새 `run_id`를 사용한다. 연구 질문·표본·환경축이 달라지는 후속 연구는 새 study ID와 별도 연구 디렉터리에서 수행한다.
