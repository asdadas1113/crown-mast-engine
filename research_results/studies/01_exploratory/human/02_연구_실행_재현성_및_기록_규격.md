# 1연구 실행 재현성 및 기록 규격

## 1. 목적

이 문서는 1연구를 실제로 실행할 때 어떤 정보를 반드시 저장해야 하는지 정의한다.

1연구의 목적은 대표적인 Crown/Mast 조건에서 넓은 roster·성장·환경 조합을 탐색하고, 전체 경향과 후속 연구가 필요한 특이 사례를 찾는 것이다. 따라서 단순히 결과 수치만 저장해서는 안 되며, 나중에 같은 조건을 다시 계산했을 때 동일한 입력과 규칙을 복원할 수 있어야 한다.

이 문서는 실행 승인 전 기록 규격을 고정하기 위한 문서이며, 현재 연구 표본은 아직 수집하지 않는다.

## 2. 재현성 원칙

각 실행은 최소한 다음 네 층을 구분해 기록한다.

1. 연구 정의: 어떤 연구와 어떤 표본 설계를 실행했는가
2. 코드 상태: 어떤 Git commit과 엔진 규칙으로 실행했는가
3. 데이터 상태: 어떤 캐릭터 데이터와 스킬 수치로 실행했는가
4. 개별 시나리오 입력: 어떤 편성·성장·전투·시간축 조건이었는가

이 중 하나라도 누락되면 정식 연구 결과로 취급하지 않는다.

## 3. 식별자

### study_id

연구 자체를 식별한다. 한 번 확정된 study_id는 같은 연구 안에서 바꾸지 않는다.

현재 1연구는 아직 실행 전이므로 최종 study_id를 확정하지 않는다.

### run_id

같은 study_id 아래에서 실제로 수행한 한 번의 실행 묶음을 식별한다.

코드 또는 데이터가 달라진 재실행은 기존 run_id를 덮어쓰지 않고 새 run_id를 사용한다.

### case_id

동일한 연구 정의 안에서 개별 시나리오 조건을 식별한다.

case_id는 편성·성장점·환경점처럼 실험 조건의 동일성을 나타낸다. 다만 case_id만으로 코드와 캐릭터 데이터의 동일성까지 보장하지 않는다. 이 때문에 run manifest의 Git commit과 catalog revision/hash를 반드시 함께 기록한다.

## 4. 실행 단위 manifest 필수 항목

각 run에는 하나의 최상위 manifest를 둔다.

필수 항목은 다음과 같다.

- `schema_version`: manifest 형식 버전
- `study_id`: 연구 식별자
- `run_id`: 실행 식별자
- `status`: draft, approved, running, completed, invalidated 등 실행 상태
- `generated_at`: 생성 시각
- `git_branch`: 실행 branch
- `git_commit`: 실행 코드의 정확한 commit SHA
- `engine_rule_revision`: 엔진 규칙 revision
- `skill_hook_revision`: skill hook revision
- `skill_hook_factories`: 실제 hook factory signature 목록
- `catalog_source_revision`: 캐릭터 데이터 source revision 전체 문자열
- `catalog_sha256`: 캐릭터 catalog 내용 해시
- `study_definition`: 후보군, 제외군, 성장 설계, 환경축, 표본 수
- `timeline_definition`: 사용한 시간축의 식별자와 실제 cycle 값
- `output_schema_version`: 결과 파일 형식 버전
- `validation_references`: 실행 전에 통과해야 하는 검증 문서와 CI/run 참조

## 5. 캐릭터 데이터 변경 실험

현재 엔진은 표준 catalog 내용에 SHA-256 해시를 붙이고, `with_skill_value()`로 수치를 변경한 경우 변경 항목과 값이 catalog revision에 추가되도록 보강되어 있다.

따라서 스킬 수치를 변경한 실험은 기존 표준 scenario의 catalog revision과 일치하지 않으며, revision mismatch가 발생하면 실행을 거부해야 한다.

정식 연구에서는 임시 스킬 수정 실험을 기본 표본에 섞지 않는다. 민감도 실험이나 진단용 override가 필요하면 별도 run 또는 별도 validation 기록으로 분리한다.

## 6. 개별 scenario 보존 항목

각 scenario 파일에는 최소한 다음 입력을 보존한다.

- `case_id`
- roster 전체
- Main/Secondary 역할 지정
- 각 캐릭터 build
  - 장비 상태
  - collection/SR 상태
  - overload ATK/Element/Ammo 줄 수
- boss DEF
- boss element
- core hit rate
- range bonus
- Main advantage 여부 또는 실제 적용된 속성 조건
- combat duration
- startup delay
- min firing rounds adjustment
- baseline rotation
- burst timeline 전체
- 예상 revision 값

애장품 캐릭터는 1연구 성장 설계에서 SR15를 canonical floor로 사용한다. 따라서 성장 프로필 이름만 저장하지 말고, 최종 해석된 실제 build 값도 scenario에 저장한다.

## 7. 결과 파일 구분

기계용 결과는 다음처럼 분리한다.

```text
machine/
├─ manifest/
├─ scenarios/
├─ raw/
├─ aggregate/
└─ provenance/
```

- `manifest/`: 실행 전체의 정의와 재현성 정보
- `scenarios/`: 실제로 실행한 입력 조건
- `raw/`: scenario별 원시 결과
- `aggregate/`: 집계 결과와 요약 통계
- `provenance/`: 실행 환경, validation 참조, 코드/데이터 상태 확인 기록

raw와 aggregate는 서로 덮어쓰지 않는다.

## 8. 정식 결과 인정 조건

아래 조건을 모두 만족해야 정식 1연구 결과로 취급한다.

1. 실행 전에 명시적 승인이 있었다.
2. manifest가 실행 전에 생성되고 study/run 식별자가 고정되었다.
3. 실행 코드 Git commit이 기록되었다.
4. catalog source revision 및 content hash가 기록되었다.
5. engine rule 및 skill hook signature가 기록되었다.
6. 모든 scenario 입력이 별도 보존되었다.
7. validation gate가 통과했다.
8. raw 결과와 aggregate 결과가 분리되어 저장되었다.
9. 실패·중단·부분 실행은 completed run과 섞지 않았다.

## 9. 현재 상태

2026-09-06 기준 연구 인프라 보강은 완료되었으나, 1연구의 최종 표본과 study_id는 아직 확정하지 않았다.

따라서 현재 단계에서는 이 규격과 폴더 틀만 유지하며 실제 연구 데이터를 생성하지 않는다.
